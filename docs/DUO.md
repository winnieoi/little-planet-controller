# 双人分屏说明

一块屏幕、两位玩家、同一张霓虹星球地图：左边一位用键鼠，右边一位用手柄；
插两只手柄时，两位各拿一只。**游戏本体一行未改**，双人能力全部由三个新文件提供。

---

## 快速开始

```bash
cd little-planet-controller
node server/server.js
```

浏览器打开：

```
http://localhost:8765/duo.html
```

进入后按一下手柄上的任意键唤醒（浏览器要求先有一次用户交互才会暴露手柄）。
顶栏会显示两位玩家的坐标、所在区域、奇迹收集进度，以及"P2 在 P1 的哪个方向"。

单人玩法不受影响，仍然走 `http://localhost:8765/`。

---

## 手柄怎么分配

分配规则只有一条，写在 `web/bridge/duo-pads.js` 里，宿主页和两个座位页共用同一份：

| 检测到的手柄 | P1（左屏） | P2（右屏） |
| --- | --- | --- |
| 0 只 | 键鼠 | 无（可用键鼠？不行 —— 见下方说明） |
| 1 只 | 键鼠 | 这唯一的一只 |
| 2 只及以上 | 第 1 只（按 `index` 排序） | 第 2 只 |

也就是说：**"一人键鼠一人手柄"和"两人各一只手柄"是同一套逻辑的两种结果**，
不需要切换模式，插上第二只手柄就自动升级。

> 只有 1 只手柄时它归 P2，是为了保住"键鼠永远控制 P1"这条不变量 ——
> 否则中途插拔手柄会让两位玩家的控制权互换。

顶栏实时显示分配结果，例如 `已识别 2 只 · P1 ← 手柄 1 · P2 ← 手柄 2`。
一只都没有时显示 `未检测到手柄（P2 可按一下手柄任意键唤醒）`。

## 布局

顶栏右上角「上下布局 / 左右布局」一键切换：

- **左右**（默认）—— 宽屏显示器、笔记本外接屏
- **上下** —— 竖屏或超宽屏

## 昼夜切换

顶栏「☀️ 白天 / 🌙 夜晚」按钮：**两个画面同时换主题**，整页重载，双方手记进度都不丢。
座位 iframe 里故意不放切换按钮 —— 两个人各切各的必然切不到一起，主题必须由宿主统一裁决。

也可以直接用地址控制：`duo.html?theme=day` 进白天，`duo.html` 进夜晚。

昼夜两版是同一构建的两套主题常量：官方原文件（夜晚版）一行未动，白天版
（`assets/index-day-*.js` / `index-day-*.css`）按官方昼夜配色逐项映射生成，
与 `preview/little-planet-preview-day.html` 的画面逐像素一致。

按键操作：

| 玩家 | 操作 |
| --- | --- |
| P1（键鼠） | `WASD` 移动、`Shift` 奔跑、`Space` 跳跃、`E` 互动、`V` 换视角、拖拽环视、滚轮缩放 |
| P2（手柄） | 左摇杆移动、右摇杆环视、`×` 跳跃、`□` 互动、`△` 换视角、`○` 取消、`L2` 奔跑、`R2`/`R1` 拉近、`L1` 拉远、触摸板镜头回正 |

完整映射见 [`DS5.md`](DS5.md)。

**键盘只控制 P1。** 点一下左边画面即可恢复键盘焦点；点右边不会把键鼠交给 P2。
座位 2 会屏蔽本机键盘的游戏按键（只拦真实键盘，不拦手柄合成的按键 —— 否则座位 2 的手柄会一起失效）。

## 玩法面板（汇总板 / 速度赛 / 信标）

顶栏下方还有一行 60px 的玩法面板，把座位上报的数据派生成三种可玩的模式：

| 模式 | 干什么 | 怎么用 |
| --- | --- | --- |
| **汇总板** | 双方累计移动距离、区域切换次数、当前区域、对局总用时 | 全自动，不需要按任何键 |
| **速度赛** | 谁先集齐 7 个奇迹谁胜。显示双方进度条与用时 | 点「开始计时」开跑；任意一方收齐即结算，胜方显示「P1 胜利 · 00:17」，点「再来一局」重开 |
| **信标** | 一方**进入新区域**或**收到新奇迹**时，对方面板弹出 8 秒提示 | 全自动，不需要新按键 |

信标的意义：两个人互相看不见，但「P2 进入 Fernwood」「P2 奇迹 4/7」这样的提示
能让 P1 知道对方大概走到了哪、进度到哪 —— 配合顶栏的八方位提示，两人就有了
最基本的「互相感知」。

三种模式共享同一份座位上报数据（`duo-state`），互不依赖，在宿主（duo.html）侧运行，
**不占座位页任何资源，也不改游戏本体**。实现见 [`bridge/duo-modes.js`](../web/bridge/duo-modes.js)。

配图 `docs/duo-modes.png`。

## 两份独立进度

两位玩家各存各的手记。游戏原本只有一个存档键 `little-planet-journal-v2`，
座位页把**本 iframe 自己 realm 的** `Storage.prototype` 打了个前缀：

```
座位 1 → duo:1:little-planet-journal-v2
座位 2 → duo:2:little-planet-journal-v2
```

每个 iframe 有独立的 realm，所以宿主页与另一个座位完全看不到这个改动。
单人玩法（不带 `?seat=`）时 `duo-seat.js` 直接退出，一行副作用都不留。

---

## 已知限制：两位玩家看不见彼此

这是**游戏本体决定的**，不是实现偷懒：

- 游戏是打包后的单行压缩产物，仓库里没有源码
- 只有一个角色、一台相机，不向 `window` 暴露任何游戏对象
- 因此**无法在同一个世界里放下两个角色**

所以两个玩家跑的是**两个独立的世界实例**：同一张地图、同一批地标、同样的奇迹点位，
但互相看不见对方。为了弥补，顶栏给出了**互相找路的工具**：

- 双方实时坐标（如 `58.1° N 143.0° E`）
- 所在区域名（如 `Fernwood`）
- 收集进度（`奇迹 3/7`）
- **八方位提示**：`P2 在 P1 的西方`（按大圆方位角计算，跨极点也不会算错）

配合语音通话，两位玩家可以约定"一起往北走到那片霓虹森林"，形成事实上的并肩探索。

---

## 已知限制：灯条与自适应扳机只在座位 2 的手柄上生效

这条是 WebHID 的边界，不是偷懒。

灯条与自适应扳机 Gamepad API 完全不提供，只能走 WebHID；而 `navigator.hid.getDevices()`
给的是**每个 document 自己的一份设备实例** —— 两个 iframe 会同时打开同一只手柄，
各按自己那份游戏状态发报文，结果是灯条来回闪、扳机阻力互相打架。

Gamepad API 靠 `index` 就能分清哪只手柄归谁，**WebHID 做不到**：设备列表的顺序与
gamepad index 没有任何对应关系，硬按顺序去配就是猜。既然分不开，就让座位 2 独占这一层，
其余座位整层停用（`lp-dualsense.js` 在 `enable` 为 false 时连设备都不碰）。

| 反馈 | 单手柄（P2 持柄） | 双手柄 |
| --- | --- | --- |
| 事件振动（跳跃、收集、换区……） | P2 有 | **两位都有**，按座位精确分流 |
| 灯条配色 | P2 有 | 只有 P2 那只 |
| 自适应扳机阻力 | P2 有 | 只有 P2 那只 |

振动走 Gamepad API，能按座位分流，所以**两位玩家的手感反馈都不缺**；
缺的只是 P1 那只手柄的灯条与扳机阻力。

## 自检页

```
http://localhost:8765/bridge/duo-selftest.html
```

页内起两个真实座位 iframe，配两个假 DualSense，覆盖 **37 项断言**：

| 组 | 覆盖内容 |
| --- | --- |
| A | 手柄归属规则（含离线手柄剔除、单手柄降级） |
| B | 快照与变化签名 |
| C | 座位接线（存档隔离、`padProvider` 优先级、键盘防护） |
| D | 分发（变化才发、心跳、看不到就不发） |
| E | 输入互不串扰（含"座位 2 的键盘防护不拦截合成按键"） |
| F | 空消息不得覆盖有效快照 |
| G | 存档隔离（`duo:1:` 与 `duo:2:` 互不可见） |
| H | 震动回传到正确手柄 |

不需要手柄也能跑，用来回归。手柄侧另有 [`ds5-selftest.html`](../web/bridge/ds5-selftest.html)（39 项断言）。

## 三个文件各管一件事

| 文件 | 职责 |
| --- | --- |
| `web/duo.html` | 宿主页：分屏布局、顶栏状态、队友方位 |
| `web/bridge/duo-pads.js` | 手柄归属规则 + 跨 frame 快照广播 + 震动回传 |
| `web/bridge/duo-seat.js` | 座位侧接线：存档隔离、手柄来源、键盘防护、坐标上报 |

`duo-pads.js` 被三方共用，是为了让归属规则只有一份实现 —— 如果宿主和座位各写一套，
两只手柄插拔时两边的判断会打架。`duo-seat.js` 在单人页也被加载，
但只在 URL 带 `?seat=N` 时才注册任何监听。

---

## 为什么不会出 bug

双人比单人多的风险全在"跨 frame 与手柄归属"上，逐一封死：

1. **归属规则单一实现。** 宿主、座位 1、座位 2 都用 `DuoPads.pick()`，
   不存在三份算法算不到一起的可能。排序按 `index`，两个页面结果必然一致。

2. **"看不到"不发言。** 广播时若本帧读不到自己该发的那只手柄，就**什么都不发**。
   早期版本会发空消息，结果座位之间互相把宿主送来的有效快照顶掉，
   表现为"P2 的手柄时好时坏"。这是唯一一次真实踩坑，已在源头修掉：
   *「我没看到」不是有效信息，静默即可。*

3. **键盘防护只拦真实按键。** 座位 2 的守卫检查 `e.isTrusted`。
   手柄适配层是通过合成 `KeyboardEvent` 驱动游戏的，若一刀切拦截，
   座位 2 的手柄会连带失效。

4. **跨 frame 手柄不能用引用判等。** 快照每帧都是新对象，
   适配层若按 `pad !== activePad` 判断"刚接入"，接入震动会每帧连发。
   适配层因此加了 `samePad()`，只比 `index` 与 `id`。

5. **存储按 realm 隔离。** 只改本 iframe 的 `Storage.prototype`，
   宿主与另一个座位的 `localStorage` 毫无变化。

6. **断线降级明确。** 宿主长时间不推快照（超过 800ms），座位会回退成自己读手柄，
   所以直接打开 `index.html?seat=2` 也能玩；拔掉所有手柄时两侧都清空输入，不留幽灵移动。

7. **硬件输出层只有一个座位在写。** 灯条与自适应扳机走 WebHID，而 WebHID 的设备是
   「每个 document 各一份」，两个 iframe 会同时打开同一只手柄、各发各的报文。
   WebHID 又无法把设备与 gamepad index 对应起来，所以这一层交给座位 2 独占，
   其余座位整层停用。两个 iframe 抢一只设备这件事因此从根上不会发生 ——
   不是"谁先谁赢"的竞态，而是根本不存在第二个写入者。

8. **自检页不吃环境。** 座位是独立 realm，宿主替换 `navigator.getGamepads` 管不到它；
   机器上若插着真手柄，座位会在快照空档期自读到它，断言就被真实输入带偏。
   所以自检页显式把座位侧的自读入口也换成受控列表 —— 插着真手柄跑，结果一样可信。
